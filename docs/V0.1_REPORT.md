# 2026-11-08 — BLE scan lifecycle fix + X18 real-hardware verified (`v0.1.5-x18-verified`)

## A. Minimal reproduction of the scan failure
Controlled A/B on real hardware, **no printing**:
- After a fresh boot, if `/api/scan` is the FIRST BLE call, scans keep working
  (8 endpoints) even after connect -> disconnect -> repeated scans.
- After a fresh boot, if `/api/connect` is the FIRST BLE call (exactly what the
  print path does), **every later `/api/scan` returns `NOT_FOUND` / 0 endpoints
  forever** — including all surrounding BLE devices — while `/api/connect`
  itself keeps succeeding. 6/6 scans returned 0.
- Repro scripts: `C:\Users\Public\rtb_scan_repro.py`,
  `rtb_scan_repro_b.py`; results `rtb_scan_repro_result.json`,
  `rtb_scan_repro_b_result.json`, `rtb_scan_repro_b_coldboot_out.txt`.

## B. Root cause
Two defects in `src/transport/ble/BleTransport.cpp`:
1. **Split initialization paths.** `scan()` configured the scanner
   (`setAdvertisedDeviceCallbacks`, `setActiveScan`, `setInterval`,
   `setWindow`) only inside its own `if (!initialized)` block. `connect()` had
   a separate init path that called `BLEDevice::init()` +
   `BLEDevice::getScan()` and then set `initialized = true` **without ever
   registering the advertisement callbacks or scan parameters**. When
   `connect()` was the first BLE operation (the normal print path), `scan()`
   skipped its configuration block permanently, so `ScanCallbacks::onResult`
   never fired and `scan_results` stayed empty -> 0 endpoints. `/api/connect`
   was unaffected because it uses the independent `BLEClient` path.
2. **Redundant `stop()` after a blocking `start()`.** `BLEScan::start(seconds,
   false)` is the BLOCKING overload: it waits for the GAP scan-complete event,
   which already sets `m_stopped=true` and gives `m_semaphoreScanEnd`. Calling
   `stop()` afterwards issues `esp_ble_gap_stop_scanning()` on an inactive scan
   (the previous round's log contained 129
   `E (...) BT_BTM: BTM_BleScan scan not active` errors) and leaves an extra
   semaphore give, corrupting subsequent scans.

## Probe (host-side BLE Central, no firmware/product-code change)
Reused `TinyProtocol::statusRequest()` (opcode `A3`, payload `[0x00]`) to
generate the exact TX frame; no protocol bytes were invented. Host Central:
`bleak 3.1.0` installed into a throwaway directory outside the workspace.
- TX: `51 78 A3 00 01 00 00 00 FF` (9 B) to
  `0000AE01-0000-1000-8000-00805F9B34FB`, mode `WRITE_NO_RESPONSE`,
  single write, success.
- NOTIFY subscribed on `0000AE02-...` successfully.
- RX (1 notification, 11 B): `51 78 A3 01 03 00 00 03 26 CD FF`.
- Validated with the project's OWN `TinyProtocol::validateFrame()` /
  `parseStatus()`: `VALIDATE=OK`, `OPCODE=0xA3`, `PAYLOAD_LEN=3`,
  `PAYLOAD=00 03 26`, `CRC=OK`, `PARSE_STATUS=OK`, `SOURCE=A3`,

- Full GATT (first time): `1800` (GAP), `AE30` with `AE01` (write-no-response),

  service here.

# 2026-11-08 — first real hardware flash / board config fix (`v0.1.2-pre-hardware`)

A one-time unfreeze to fix **only** the `s3_n16r8` board memory configuration.
No eFuse was written or modified. No product code, protocol, queue, BLE, HTTP,
SuperMini or WROOM-32E target was changed.

## The defect (found only on real silicon)
Flashing `v0.1.1-pre-hardware` to the connected ESP32-S3 N16R8 produced an
infinite boot loop:
```
E (314) cpu_start: Octal Flash option selected, but EFUSE not configured!
abort() was called at PC 0x40376bc1 on core 0
Rebooting...   (rst:0xc RTC_SW_CPU_RST, ~2.5 boots/second)
```
Read-only `esptool` facts: `ESP32-S3 rev v0.2`, `Detected flash size: 16MB`,
`Flash type set in eFuse: quad (4 data lines)`. PlatformIO's
`builder/main.py` sets `build_boot = "opi"` for `memory_type = opi_opi` /
`opi_qspi`, i.e. it builds a bootloader that requires an **octal flash** eFuse.
The N16R8 module has 16 MB **quad/QIO** flash plus 8 MB **OPI PSRAM**, so
`opi_opi` (octal flash + octal PSRAM) was simply the wrong variant. Compiling
successfully had never exercised this path.

## The fix
`platformio.ini`, `[env:s3_n16r8]` only:
```
- board_build.arduino.memory_type = opi_opi
+ board_build.arduino.memory_type = qio_opi
```
`qio_opi` is one of the shipped ESP32-S3 SDK variants and keeps OPI PSRAM.
`s3_supermini` stays `qio_qspi`; `wroom32e_future` is untouched.

# Final freeze fix 2026-11-07 — dedup semantics + UBSAN

Very limited last repair before freezing. No other functionality was added.

**Problem:** `PrintQueue` used both `job_id` and `content_hash` for dedup, so
identical content under a different `job_id` was rejected as `duplicate_job`.
That also broke the documented `uncertain_partial` recovery path (manual
reprint with a new `job_id`).

**Fixed rules** (`src/app/PrintQueue.{h,cpp}`, two isolated key namespaces):
- `job_id` non-empty -> `dedup_key = job_id`; idempotency by `job_id` **only**.
  Identical content under a different `job_id` is accepted.
- `job_id` empty -> `dedup_key = content_hash`; protects no-ID requests
  against accidental resubmission.
- A content hash never blocks a request carrying a valid `job_id`.
  `seen()` / `remember()` now carry a `id_based` flag, so a `job_id` that
  happens to equal a hash string cannot collide either.
- `markDone()` / `markFailed()` only remember the key that was actually used;
  `markUncertainPartial()` stays out of `recent_`, so a frozen job occupies
  only the `job_id` namespace.

**Files changed:** `src/app/PrintQueue.{h,cpp}`,
`tests/host/test_main.cpp`, `tools/run_mock_tests.ps1`, `README.md`,
`docs/HARDWARE_TEST_PLAN.md`, this report. Added
`tests/host/ubsan_canary.cpp`.

**Required regression cases (all PASS):** (1) `A+X` OK, repeat `A+X`
`duplicate_job`; (2) `A+X` OK then `B+X` OK; (3) no-ID `X` OK then no-ID `X`
`duplicate_job`; (4) `A` frozen as `uncertain_partial` then manual `B+X` OK;
(5) queue / offline retry / uncertain_partial / ASAN / profile consistency all
still pass. Extra coverage: same content after `A` is done, both namespace

Added: `src/app/Discovery.{h,cpp}`, `tests/host/asan_canary.cpp`.

## B. Callback lifetime fix
- `PrinterTransport` now documents a lifetime contract: `subscribe()` replaces
  the callback, `subscribe({})` / `unsubscribe()` drops it, `disconnect()` and
  the destructor must drop it too.
- `PrintSession` no longer captures `this`. It owns a `std::shared_ptr<State>`
  and registers a lambda capturing only `std::weak_ptr<State>` plus a protocol
  pointer; `weak_ptr.lock()` fails once the session dies. New `end()` and the
  destructor unsubscribe explicitly.
- `MockTransport` and `BleTransport` clear the callback on `disconnect()`
  (and `BleTransport` also on spontaneous `onDisconnect`); the BLE notify
  trampoline additionally checks the live connection flag.
- Regression: subscribe -> destroy session -> push notification. Both a normal
  Mock and a deliberately hostile transport that retains a stale callback copy
  are exercised; the dead session is never entered.

## C. Mirror overflow fix
`TinyProtocol::printRow()` replaced `uint8_t mirrored[64]` with a bounded
`std::vector<uint8_t>(row_bytes)` and an explicit `row_bytes > kMaxRowBytes`
(255, the frame payload limit) rejection. 384-dot / 48-byte GB01 behaviour is
unchanged. Tests cover 48, 96, 128, 255 and 256-byte rows.

## D. Scan fallback fix
New `src/app/Discovery.cpp` (transport-agnostic, host-testable) implements two
phases: AE30-filtered scan first; if no implemented Tiny/iPrint profile is
matched, a second scan with **no service UUID filter** so `DeviceCatalog` can
use name patterns, advertisement evidence and fingerprint. `prepareConnectEndpoint()`
always fills service/write/notify UUIDs from the resolved profile, so the final
`connect()` still performs full GATT AE30/AE01/AE02 verification — the fallback
does not weaken the connect check.

## E. Partial-print semantics
New terminal `JobState::UncertainPartial`; `PrintJob` records `rows_attempted`
/ `rows_dispatched` and `last_error`; `PrintSession` exposes both counters;
pure `classifyJobOutcome(result, rows_attempted)` decides `Complete` /
`SafeRetry` / `UncertainPartial`. Failure before any row is attempted stays
`waiting_printer` (auto retry). Once print data has been sent the job is frozen,
excluded from `pending`, never auto-reprinted, and requires a human decision.
**Physical exactly-once is explicitly NOT claimed.**

exactly-once; `uncertain_partial` requires human inspection and a new `job_id`
for any manual reprint; queue is RAM-only and bounded (uncertain records may be
evicted when full); HTTP debug API is unauthenticated; open AP `RTB-V0.1-AP`
has no password; OTA is an interface reservation only; no persistence, no
formal auth, no Classic Bluetooth implementation. All intentionally out of
scope for this hotfix.

**Stop point:** freeze `v0.1.1-pre-hardware`, wait for the real 喵喵机.

                       └─ EscPos / PeriPage / Paperang (LATER stubs)
                                      │ uses only

                       ├─ BleTransport (IMPLEMENTED, PIMPL, no BLE header in .h)
                       ├─ BluetoothClassicTransport (RESERVATION ONLY)

## C. Transport / Protocol layering

- `PrinterTransport`: `scan / connect / disconnect / write / read / subscribe /
  isConnected / getCapabilities`. Owns radio I/O, GATT discovery, chunking,
  notify registration. Knows nothing about opcodes.
- `PrinterProtocol`: `init / printRow / finish / feed / statusRequest /
  parseStatus`. Owns framing `51 78 <op> 00 <len16le> <payload> <crc8> FF`,
  CRC-8 (poly `0x07`), init commands, bitmap rows, feed, status parsing.
  Never scans, connects or chunks for a radio.
- `PrintSession` owns stateful behaviour (notify subscription, 0xAE flow
  control, >= 8 ms row pacing, 30 s status watchdog).
- `DeviceCatalog`/`DeviceProfile` decide *which* protocol + transport + geometry
  to use from advertisement evidence; they do no I/O.
- Demonstrated by tests: the exact same `TinyProtocol` produced identical frame
  streams over `MockTransport` (BLE emulation) and `BtClassicMockTransport`
  (SPP emulation). An `EscPosProtocol` can later use BLE / Classic / USB / TCP
  without protocol changes.
- `BoardCapabilities`: `wifi, ble, bluetooth_classic, psram, psram_size,
  flash_size, ota, dual_core`. ESP32-S3: `wifi=true, ble=true,
  bluetooth_classic=false`. Future WROOM-32E: `bluetooth_classic=true` (chip
  capability), but the Classic transport stays unavailable.

## F. Future WROOM-32E compatibility design

- Target `wroom32e_future` (`esp32dev`, 4 MB, `RTB_TARGET_WROOM32E=1`) builds
  successfully: RAM 17.9% (58780 B), Flash 51.8% (1628417 / 3145728 B).
- Finding: the default 4 MB `default.csv` (1.25 MB app slots) could NOT fit the
  WiFi+BLE+WebServer firmware; `huge_app.csv` (single 3 MB slot) was used.
  Production OTA therefore needs a bigger flash or a reduced feature set.
  **Flash/PSRAM part numbers are deliberately not locked.**
- `BoardCapabilities.bluetooth_classic=true` on that chip; the Classic
  transport still returns `NOT_IMPLEMENTED`. SPP/RFCOMM entry points are listed
  in `src/transport/bt_classic/BluetoothClassicTransport.h`.
- No WROOM-32E board on the desk: **no hardware verification, no Classic
  validation**. Single-chip dual-mode ESP32 is the production direction; an
  S3 + external Classic module is explicitly rejected.

## G. Tiny/iPrint implementation status

Implemented: BLE scan, AE30/AE01/AE02 service + characteristic discovery,
protocol fingerprint, connect, mandatory notify subscription, init sequence
(`A3, A4, BD, AF, BE, [A6]`), CRC-8 framing, bitmap rows (48 B/384 dots,
optional bit mirroring), lattice start/end (profile-controlled), feed chunking,
status parsing (`A3` flags, `A8`, `AE` flow control), disconnect, reconnect,
offline wait and **pre-print** auto recovery, keepalive status request.
Mid-job failures are frozen as `uncertain_partial` and are never auto-reprinted:
physical exactly-once is not claimed. Bitmap rows are bounded to 255 bytes, and
discovery falls back to an unfiltered scan when AE30 is not advertised (both
added in the 2026-11-07 hotfix).
Profile-driven differences for GB01 / GB02 / MX06 / SC03h (energy, speed,
lattice, mirror, write chunk, feed).
**All of the above is compile + Mock verified only — no real printer was
contacted, and no real print succeeded.** Conflicting upstream protocol details
are recorded in `docs/OPEN_SOURCE_AUDIT.md` and must be resolved on hardware.

## K. Known limitations

1. **No real printer** — every BLE/protocol result is compile + Mock verified.
2. **No WROOM-32E board** — Classic Bluetooth is architecture-only;
   `NOT_SUPPORTED_ON_THIS_TARGET` on S3, `NOT_IMPLEMENTED` on capable chips.
3. No boards were flashed/run: S3 N16R8 and SuperMini are compile-verified only.
4. `TinyProtocol.cpp` is a compact independent implementation of public
   protocol facts rather than a vendored mature library (so it can be host-
   compiled and decoupled from transport). Swappable later.
5. Bitmap pipeline is minimal (threshold -> 1bpp packing -> mirror); no
   dithering, QR, barcode, fonts, image decode, ESC/POS raster parser.
6. Wi-Fi/BLE coexistence is a simplified single-loop `setBleBusy()` +
   reconnect kick, not the full dual-core split from `ahmetozer`.
7. Queue is RAM-only (no persistence across reboot) and bounded (16 jobs,
   64 KB/job). **No physical exactly-once guarantee**: once print data has been
   sent, a failed job is frozen as `uncertain_partial` (with
   `rows_attempted` / `rows_dispatched` / `last_error`), excluded from
   `pending`, and never auto-reprinted; a human must inspect the paper and
   decide on a manual resubmit with a new `job_id`. That manual reprint is now
   accepted even with identical content, because dedup is by `job_id` only.
   Only failures before any row was attempted are auto-retried
   (`waiting_printer`). Uncertain records may be evicted if the bounded queue
   becomes full.
8. OTA is an interface reservation only (`501 NOT_IMPLEMENTED`); the WROOM-32E
   target currently uses a single app slot (`huge_app.csv`).
9. **HTTP debug API has no authentication** (any client on the LAN can enqueue
   jobs, switch Mock mode, disconnect the printer). The fallback AP
   `RTB-V0.1-AP` is **open / unencrypted**. Both are known V0.1 limitations,
   deliberately not addressed in this hotfix (no formal auth, no website,
   templates, cloud, users or payments — all LATER).
10. Protocol conflicts listed in the audit (CRC example, feed byte order,
    bit order, lattice, energy byte order) require real hardware to settle.
11. `DeviceProfile` JSON files must stay in sync with `BuiltinProfiles.cpp`;
    `tests/test_profiles.py` enforces this but the sync is manual.
12. Windows/xtensa cannot read non-ASCII paths, hence the ASCII build mirror
    in `tools/build.ps1` / `tools/run_mock_tests.ps1`.

13. ASAN host coverage is x86-64 Windows only; the ESP32 firmware itself was
    not run under a sanitizer and was not flashed to any board.

**Stop point:** after the 2026-11-07 hotfix, freeze `v0.1.1-pre-hardware`.
No further website / payment / template / extra-protocol / Classic Bluetooth /
OTA / PCB / persistent-queue / auth work until a real printer arrives and the
hardware test plan is executed.
